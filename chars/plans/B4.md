# Package B4: Touch and mobile support

## Package-specific instructions
- Full touch control scheme for phones and tablets (landscape): left virtual joystick (throttle + steering), right half drag to aim the turret / look, big FIRE button, MG button (hold), sight toggle, shell selector (tap the shell icons), zoom slider in the sight, smoke launcher and commander-hatch buttons, pause button. Multi-touch safe, no accidental page zoom, buttons sized >= 48 css px, layout adapts to the viewport and notches (safe-area insets).
- Detect touch-first devices (pointer: coarse / touch events) and show the touch layer only then (or when the user touches the screen); hide mouse-specific hints; menus fully usable by touch (scrollable panels, no hover-only actions, the 3D showcase orbit by drag).
- Portrait orientation: show a 'rotate your device' overlay.
- Mobile performance preset: lower DPR cap, fewer particles, shadow size, detected automatically on first launch (user can override in Options).
- Feed the central input/control state introduced by package B3; the gunner sight and the tutorial must work with touch (tutorial step texts adapt to touch).
- Test with playwright device emulation (hasTouch, isMobile, e.g. 844x390 iPhone landscape) and take screenshots into your scratch dir.

## Audit findings to implement (verify each against the current code first: line numbers may have shifted since the audit; earlier packages may have changed things)

### [feel00] No touch controls: the game cannot be played on phones or tablets (large share of CrazyGames traffic)
- kind/impact/effort: feature/5/L
- files: chars/game.js, chars/index.html
- where: game.js inputs l.4277-4353 (keyboard and mouse only), playerInput l.2323-2337, every document.pointerLockElement===cv test (trackMouse l.4319, sight mousemove l.4331, sightCam l.2569, updateCam3 l.2658), drawHUD l.3346, drawTankPanel l.3509
- problem: There is no handler for touch events, pointerType 'touch' or the Gamepad API anywhere (grep found none). Driving only works through keys.KeyW/S/A/D/arrows; switching shells, sight, smoke, camera and machine gun are all keyboard-only. On a touchscreen, a tap produces an emulated mousedown that fires a shell and requests pointer lock (which fails), so the player can shoot where they tap but cannot drive, open the sight or switch shells. The battle is unplayable on mobile and tablets.
- proposal: Add a 'Touch controls' section after the inputs. Enable it with matchMedia('(pointer: coarse)') or on the first pointerdown with pointerType==='touch'. State: touch = {on, stick:{id,ox,oy,dx,dy}, aim:{id,lx,ly}, fire, mg, rects:[]}. On cv, add pointerdown/move/up/cancel handlers for touch pointers. They call e.preventDefault(), which suppresses the emulated mousedown that currently fires and requests pointer lock, and setPointerCapture.
(1) LEFT STICK: a touch in x < 0.4W that is not on a button creates a floating stick at the touch point, radius R = 56 px, deadzone 0.15. It produces thr = -dy/R and turn = dx/R. In playerInput: thr = clamp(kbThr + touch.thr, -1, 1), same for turn. updateTank already accepts analog values (l.1050: clamp(inp.throttle), target = thr*vmax).
(2) RIGHT-SIDE AIM: dragging elsewhere behaves like a locked pointer. In the outside view: mouse.x += dx*sens*1.4 and mouse.y += dy*sens, clamped to 0.25H..0.7H. In the sight: sight.cx += dx*0.8, sight.cy += dy*0.8. Add isLocked() = pointerLockElement===cv || touch.on and use it in the four places listed, so the existing 'cursor stays on terrain while the camera turns' logic works unchanged.
(3) BUTTONS drawn by a new drawTouchUI() on the 2D context, with their rectangles stored for hit tests: FIRE, a 44 px circle at (W-84, H-96) with the reload ring (reuse rf); SIGHT, which toggles setSight; MG, held to set touch.mg (player.in.mg |= touch.mg); SMOKE (deploySmoke); CAM (cycle CAM_MODES); PAUSE (≡, top-left); a SHELL chip that cycles through owned SHELL_KEYS, with a long press opening a radial of 7. A two-finger pinch changes sight.mag in the sight and cam3.dist outside.
(4) The spectator 'tap to switch ally' moves from mousedown to pointerdown.
(5) In touch mode: quality defaults to 'basse' on first launch, pointer lock is never requested, the module chip row of the tank panel is hidden and the shell list becomes a vertical strip at the right edge.
Verify with Playwright using hasTouch:true, isMobile:true, viewport 844x390: drag the stick with CDP Input.dispatchTouchEvent and assert __fa.player.speed > 20; tap FIRE and assert stats.shots increments; tap SIGHT and assert __fa.sight.on.

### [comp12] No touch controls: the game must be flagged desktop-only and touch devices need a clear notice
- kind/impact/effort: compliance/3/S
- files: chars/game.js, chars/index.html
- where: playerInput() ~2323-2338 (keys and mouse only), input section 4277-4352; index.html viewport meta line 5
- problem: Driving, aiming and firing read only the keys{} map and mouse events, and no touchstart or pointer-based battle controls exist (the word 'touch' only appears in comments). On phones and tablets the menu works through tap-to-click, but Deploy leads to a battle that cannot be played. If the game is submitted as mobile-friendly it fails QA; if it is desktop-only, tablet and touchscreen users still reach a broken battle.
- proposal: Submit as desktop-only. Detect touch-primary devices with matchMedia('(pointer: coarse)').matches && !matchMedia('(any-pointer: fine)').matches (or SDK.user.systemInfo.device.type when available). Replace the Deploy CTA with a 'Keyboard & mouse required' card, and hide the controls help. Longer term: a virtual stick plus fire, sight and shell buttons drawn on #game, feeding player.in.

### [comp17] Menu layout breaks at small 16:9 iframe sizes
- kind/impact/effort: polish/2/S

For the HUD, scale the bottom panel and readouts with S, and move the range readout above the ready-rack text when W < 760.

## PRIORITY USER REQUEST: iPad with a hardware keyboard (do this first)
The user plays on an iPad with a keyboard (Magic Keyboard / Smart Keyboard, maybe a trackpad). Today the touch detection (body.touch, #touchNote 'Keyboard & mouse required', #startBtn hidden on touch) blocks the game on iPad. Required:
- Never block play on touch devices: Deploy is always available; remove/replace the 'Keyboard & mouse required' notice (touch controls exist after this package).
- Hybrid input: any keydown switches to keyboard mode (hide the touch layer, keyboard hints back); a touch on the screen shows the touch layer again; mouse/trackpad pointer events (pointerType 'mouse') work for aiming and firing as on desktop, including iPadOS trackpad (no pointer lock on Safari iPadOS: aiming must work without pointer lock, with the cursor drawn in the sight).
- iPadOS Safari specifics: key events use e.code (WASD/arrows/Space/Shift/Esc may not exist: Esc is often missing on iPad keyboards, so also map the backquote key `/§ and P to pause), prevent page scroll/zoom, audio unlock on the first touch or key, fullscreen not available (do not rely on it), 100vh issues (use dvh / innerHeight), safe-area insets.
- Mixed usage: a player can drive with the keyboard and aim/fire by touching the screen at the same time (keyboard + touch layers both active when both are used).
- Test with playwright emulating an iPad (hasTouch, isMobile false or true, viewport 1180x820, userAgent iPad) and sending keyboard events.
